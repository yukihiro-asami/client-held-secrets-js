# クライアント保管の秘密情報によるオンデマンド・サーバー処理

[English](README.md)

2026-10-31更新。既知技術を組み合わせた構想と、その参照実装を説明する。架空番号を対象にした試作と開発VPSでの実証を終え、[単独で起動できる例](example/README.ja.md)を用意した。レビュー後の修正と独立配置での検証を完了した。製品全体の完成を意味しない。

## 使い方から見る構想

一度入力した秘密情報を自分のブラウザに保存し、必要なときだけ提供元に渡して使う。提供元は依頼された処理の間だけ内容を読み、処理後は秘密情報を残さず、何のために使ったかという記録を残す。毎回入力する手間を減らしながら、提供元に大量の秘密情報が長期間たまることを避ける構成である。

架空のカード番号なら、「入力してブラウザに保存 → 対象と用途を確認 → 番号の形式確認に使う → 提供元の署名付き記録を確認する」という流れになる。保存中の番号は入力時に平文で確認でき、保存成功後は入力欄を空にして、末尾4桁だけを表示する。保存操作では番号を送信しない。参照実装は形式確認を行うだけで、決済は行わない。

## 目的と対象

秘密情報を利用者のブラウザに保存し、利用者が依頼する処理に必要なときだけ、暗号化して提供元へ渡す。提供元は復号して指定された処理に利用し、一時データを破棄する。毎回の入力を減らす利便性と、提供元が秘密情報をできるだけ保有しないことを両立する。

対象は、盗む動機が強く、失った場合に利用者が再入力できる秘密データとする。提供元には、利用者の秘密情報の暗号文を長期保管しない。大量の秘密情報が提供元のDBに蓄積される構造を避けることが、この構成の中心である。

提供元は依頼された処理の間には平文を扱う。提供元にも内容を読ませない方式ではない。既存の鍵交換・鍵導出・認証付き暗号・署名を組み合わせた構想として示す。

## 方式の概要

保存と受け渡しで鍵を分ける。手元の原本はブラウザの保存用鍵で暗号化し、利用時だけ復号する。受け渡しでは、利用者と提供元のX25519鍵から共有秘密を得て、HKDFで共通鍵を導出する。その鍵で、今回必要な情報を認証付き共通鍵暗号により暗号化する。

HTTPSに加えるこの暗号層は、TLS終端や中継プロキシでは内容を暗号文に保ち、指定した提供元処理で復号するために使う。

アプリは対象と用途を示すマニフェストを作り、暗号文とともに送る。この本文全体を[参照実装に含めたEd25519要求認証](example/PROTOCOL.md)に結び付ける。提供元は認証・権限・依頼内容の対応を確認してから復号し、処理後には秘密情報を含めない署名付き利用記録を残す。

## 提供元での集中保管方式との比較

比較対象は、提供元が秘密情報をDBへ暗号化保存し、DBとは分離した鍵または復号機能を使って必要時に復号する構成とする。平文保存を比較対象にせず、両方式ともHTTPSを使い、処理中は提供元が平文を扱うものとする。

### 保管場所と利用できる時点

| 観点 | 提供元で暗号化して集中保管 | 本提案 |
|---|---|---|
| 原本の継続保管 | 提供元のDBに暗号文を蓄積する | 利用者のブラウザに暗号化保存する |
| 提供元へ渡すタイミング | 登録・更新時に渡し、以後は提供元が保存情報を読む | 必要な処理を依頼する際に、その処理に必要な情報を渡す |
| 提供元が復号できる対象 | 保存済みの情報のうち、復号権限が及ぶもの | 今回受け取った情報。提供元には過去の情報を復号するための保管暗号文がない |
| DBだけを持ち出された場合 | 適切に分離された鍵が得られなければ、暗号文の取得だけで平文を読めるとは限らない | 対象の秘密情報の暗号文自体が提供元DBにない。業務データや利用記録は別に保護する |
| DBに加えて復号機能も侵害された場合 | 権限が及ぶ範囲の保存情報が、まとめて復号され得る | 過去の秘密情報の集中保管庫がないため、同じ方法で過去分をまとめて取り出せない |
| 処理後に提供元に残すもの | 継続利用する暗号文と、必要な業務記録 | 秘密情報を含めない業務記録・署名付き利用記録。一時的な暗号文・平文・導出鍵は破棄する |

主な差は、暗号方式を強くすることよりも、提供元に保管する秘密情報の量と期間を変える点にある。集中保管では蓄積した情報へのアクセスを制御する。本提案では、その蓄積自体を利用者側へ移し、提供元が扱う範囲を依頼された処理へ絞る。

X25519・HKDF・認証付き暗号は、この利用時の受け渡しを実現する部品である。提供元も受信時には復号できるため、導出鍵を捨てるだけで保存済み暗号文を永久に復号不能にする方式ではない。提供元が暗号文を長期保存せず、処理後に一時データを破棄することと組み合わせて成立する。

### 利用者の操作と運用

| 観点 | 提供元で暗号化して集中保管 | 本提案 |
|---|---|---|
| 同じブラウザでの繰り返し利用 | 提供元の保存情報を使うため再入力不要 | 手元の保存情報を使うため再入力不要 |
| 別ブラウザ・新しい端末 | 同じアカウントで保存情報を利用しやすい | 初期構成ではそのブラウザで再入力する |
| ブラウザの保存領域の消失 | 提供元の原本は残る | 原本または保存用鍵を失った情報は再入力する |
| 利用者がブラウザを開いていない間の処理 | 保存情報を使う定期処理・バックグラウンド処理を構成できる | 新たな秘密情報の提供はブラウザからの依頼を起点とする。完了した処理の情報を後日使う構成にはしない |
| バックアップと復旧 | 提供元が秘密情報の暗号文と復号手段の復旧を管理する | 提供元で利用者の秘密情報を復旧する仕組みを持たず、利用者の再入力で再開する |
| 利用の記録 | 保管方式とは別に設計する。署名付き記録も追加できる | 対象・用途を示す依頼と、秘密情報を含めない署名付き利用記録を構成に含める |

このため、本提案は「何度も使うが、失った場合には再入力でき、利用時にブラウザから渡せる秘密情報」に適する。複数端末からの即時利用や、利用者が不在の間も保存情報を使い続けることを重視する用途では、集中保管の利便性がある。署名付き利用記録は、本提案と組み合わせる運用上の要素であり、手元保存だけから自動的に得られる性質ではない。

## 鍵と保持情報

| 役割 | 保持・使用するもの |
|---|---|
| 手元保存 | ブラウザの保存用AES-GCM鍵、暗号文と必要な付随情報。IndexedDBでアプリ・利用者ごとに区別する |
| 受け渡し | 利用者と提供元がそれぞれ保持するX25519鍵ペア。公開鍵を使って共有秘密を得て、HKDFで受け渡し用の鍵を導出する |
| 要求の認証 | 利用者のEd25519認証鍵。依頼本文を含む要求に署名する |
| 利用記録への署名 | 提供元の記録署名用Ed25519鍵。認証・鍵交換の鍵とは役割を分ける |

製品では保存用AES-GCM鍵を、取り出し不可のWebCrypto鍵としてIndexedDBに保持する。保存用の鍵と利用者のX25519鍵はアプリ・利用者・ブラウザごとに再利用する。提供元の受け渡し用の鍵が変わっても、手元の原本を暗号化し直す必要はない。

利用者の秘密鍵を提供元に預けたり、暗号化用公開鍵を復旧のために預けたりする構成は採らない。利用者に手動の鍵管理や復元を求めず、保存情報を失った場合は再入力で再開する。

提供元の秘密鍵は業務データやソースコードと分離し、アクセスを限定したサーバー設定として管理する。`.env`等から読み込む程度の簡潔な構成を基本とし、配置と権限設定は実装で定める。

## 各部品の役割

| 役割 | 現在の基本版 | 役割の範囲 |
|---|---|---|
| 手元保存 | WebCrypto AES-256-GCM・取り出し不可鍵・IndexedDB | 保存レコードの暗号化と内容・文脈の改変検出 |
| 受け渡し | X25519・HKDF-SHA-512・AES-256-GCM | 双方が受け渡し用鍵を得て、暗号文と対象・用途等の対応を確認する |
| 要求認証 | 利用者のEd25519認証鍵 | 登録鍵と要求本文・送信先を結び付ける。操作権限は提供元が判定する |
| 利用記録 | 提供元の専用Ed25519署名鍵 | 信頼する公開鍵に対応する署名と、記録の改変有無を検証する |
| 通信 | HTTPS | 接続先と通信路を確認する。提供元の公開鍵もこの経路から取得する |

利用者のX25519公開鍵は鍵交換に使い、登録済みの本人認証鍵としては扱わない。誰の要求かはEd25519要求署名で確認する。認証付き暗号のタグによる検査とログイン認証は別の役割である。提供元が復号した後の利用目的は、暗号だけで制限されるものではなく、提供元の処理実装が守る。

## 暗号方式と実装上の選択

受け渡しには、暗号文の改変も検出できる現行の認証付き共通鍵暗号方式を用いる。具体例はChaCha20-Poly1305とAES-GCMである。方式・鍵長・nonce・タグ・鍵導出の具体的な組み合わせは各実装仕様で定め、送受信側で一致させる。

NIST標準の暗号方式を使うことが要件となる場合にはAES-GCMを選択する。この選択は、製品全体の認証や適合性を意味するものではない。現在の製品設計ではWebCryptoとAES-GCMを受け渡しに使い、手元保存にもAES-GCMを採用している。構想としての方式の選択肢と、この製品実装の選択を区別する。

X25519鍵ペアは継続利用し、処理時に得た共有秘密と導出鍵を一時的に扱う。この破棄方針は、毎回新しい鍵ペアを交換するという意味ではない。

## 要求と処理の流れ

1. アプリが、対象と用途を示すマニフェストを構成する。利用者に手書きを求めない。
2. ブラウザが必要な情報を手元の保存用鍵で復号する。
3. 利用者のX25519秘密鍵と提供元の公開鍵から共有秘密を得て、HKDFで導出した鍵で受け渡し用に暗号化する。
4. マニフェスト、暗号文、利用者の公開鍵と必要な付随情報を要求本文にまとめる。Ed25519認証で本文を含む要求に署名し、HTTPSで送る。
5. 提供元が要求の認証、操作権限、依頼内容の対応を確認する。不一致や権限不足は拒否する。
6. 提供元のX25519秘密鍵と受け取った公開鍵から同じ共有秘密・共通鍵を導出し、復号して指定された処理に使う。
7. 成功・失敗にかかわらず一時データを後処理する。試作・参照実装では、形式確認が成功して完了したときに署名付き利用記録を残す。全拒否要求の署名付き失敗記録を作る仕様ではない。

マニフェストだけの別署名は追加しない。送信先・ログイン・本文の結び付けは既存の要求認証を使う。同一要求の再送や通信失敗時の再試行についてもその設計を引き継ぎ、必要な二重実行防止は業務操作で扱う。

## 破棄と利用記録

提供元が受信した暗号文、復号した秘密情報、共有秘密、導出した共通鍵は、処理中だけメモリに置く。DB・ファイル・ログへ保存しない。処理終了時にこれらを破棄し、利用者側の原本と継続利用する鍵は保持する。参照実装では変更可能な一時バッファを上書きし、不要な参照や入力表示を保持し続けない。JavaScriptの文字列や暗号API・OS内部の物理メモリまで消去を証明する意味ではない。

利用記録は、誰が・いつ・何を対象に・どの処理を依頼し・どういう結果になったかを表す。秘密情報そのもの、要求本文、マニフェスト全文は記録しない。提供元が記録一件ごとに署名し、記録・署名・対応する提供元公開鍵で検証できるようにする。鍵更新後も過去の記録の検証に必要な公開鍵を保持する。

DBには署名対象の完了記録と、同じ暗号化要求の再送を判別するSHA-512ハッシュを保持する。要求本文や暗号文は保持しない。「何も記録しない」という構成ではない。

参照実装では提供元の公開鍵を同じHTTPS経由で取得して署名を確認し、記録を画面に表示する。後日独立して検証するには、記録と信頼する公開鍵の保持が必要になる。

この署名が示すのは、記録が対応する提供元の秘密鍵で署名され、その後に改変されていないことである。秘密情報の破棄そのものや、記録の欠落がないことを証明する仕組みではない。

## どこまで保護するか

本構成は、提供元DBに蓄積した秘密情報をまとめて持ち去る経路をなくすことを狙う。HTTPSによる接続先確認と配信コードを信頼する前提であり、配信コードまで侵害された場合には、ページを開いた利用者の保存情報も読み出され得る。

ブラウザで任意の同一オリジンコードを実行された場合、そこに保管した番号を保存鍵で復号され得る。取り出し不可鍵は、秘密鍵のexportを制限しても、コードによる鍵の使用を禁止するものではない。端末全体の侵害や保存領域の持ち出しへの保護も環境の鍵保存に依存する。

提供元のX25519秘密鍵を保持するため、その鍵と過去の通信を取得された場合の前方秘匿性は持たない。利用者側だけを毎回新しい鍵にしても、この性質は変わらない。

署名付き記録は、物理メモリの消去、用途外利用の不在、記録の無欠落を証明しない。番号自体を記録しないため、特定のカード番号を使用した証明にもならない。

## 継続利用と情報の消失

| 場面 | 動作 |
|---|---|
| 再読込・ブラウザ再起動 | 保存情報と鍵を再利用する |
| ログアウト・再ログイン | 手元の保存情報と鍵を保持する。提供元への依頼は有効なログイン状態で行う |
| 別ブラウザ | そのブラウザで鍵を生成し、秘密情報を再入力する。初期構成では同期・移送しない |
| 保存情報または保存用鍵の消失 | 読めなくなった情報を再入力する |
| X25519鍵だけの消失 | 新しい鍵ペアを生成する。手元の保存情報の再入力は不要 |

認証鍵を失った場合の利用再開と、秘密情報を失った場合の再入力は別に扱う。

## 実装と参照実装

[参照実装と起動手順](example/README.ja.md)、[通信仕様](example/PROTOCOL.md)、[検証結果](example/VALIDATION.md)を用意した。暗号パラメーター・要求形式・再送と結果照会・記録形式は具体的に定義している。方式の構成はHPKEの通信形式や安全性の議論をそのまま継承するものではない。

WebCrypto版を実用上の基本とする。独自JS版は概念説明に合わせて作った参照実装であり、アルゴリズムと計算手順を理解して自力実装できる著者の能力を、コード・実装上の工夫・検証結果で示すために添える。独自版を実務で採用する必要性は小さく、WebCryptoより優れているという主張はしない。

| 部分 | WebCrypto基本版 | 独自JS参照版 |
|---|---|---|
| 手元保存・要求認証 | WebCrypto、既存Ed25519要求認証 | 同じ共通部品 |
| 受け渡し | WebCrypto X25519・HKDF-SHA-512・AES-256-GCM、Node標準暗号で受信 | cryptos-js X25519・HKDF-SHA-512・ChaCha20-Poly1305で送受信 |
| 記録署名と検証 | Node標準Ed25519・WebCrypto | cryptos-js Ed25519 |
| 受け渡し秘密鍵 | 取り出し不可CryptoKey | 共通保存鍵でラップし、独自計算中にバイト列で使用 |

独自版も保存と要求認証にWebCryptoを使う。異なるAEADの暗号文は互換でなく、固定した方式と世代で取り違えを拒否する。独自JS版のBigIntの定時間性・物理メモリ消去は保証しない。[cryptos-js](https://github.com/yukihiro-asami/cryptos-js)の固定版とMIT表示を同梱し、原ライブラリは改変していない。

元の試作はChromeと専用DBで検証し、開発VPSで再起動・再配備後の継続利用まで確認した。切り出した両版については別途[本例の検証結果](example/VALIDATION.md)を示す。本人確認は試験用であり、実決済、Safari・Firefox・実機iOS、メモリの非残存を実証したものではない。
